# 智能体开发工作流

本流程适用于功能、修复、重构、文档和 Harness 任务。用户最新确认的范围高于旧计划与仓库遗留实现。

## 1. 任务就绪

开始实施前，任务至少应明确：

- 目标与可观察结果。
- 非目标。
- 允许修改和禁止修改的范围。
- 验收标准与验证命令。
- 是否允许网络、真实账号、GUI、外部写入、提交和推送。

缺少的信息能通过范围内只读检查确认时直接查证；只有关键分歧仍存在时才每次询问一个问题。

## 2. 工作区准备

1. 执行 `git status --short --branch`，识别并保留用户已有修改。
2. 执行 `git remote -v`，确认推送目标和上游边界。
3. 读取 `AGENTS.md`、目标代码、直接相关测试和任务规格。
4. 复杂任务使用独立分支或 worktree；简单只读任务不创建额外工作区。
5. 将任务拆成可独立验证的纵向切片，每个切片只承载一种可审查行为。

## 3. RED → GREEN → 回归

对每个行为：

1. 写一个最小失败测试。
2. 运行并确认失败原因是目标行为缺失，而不是导入或环境错误。
3. 实现使该测试通过的最小代码。
4. 重跑定向测试。
5. 运行受影响模块的回归测试。
6. 检查 diff，删除本次改动直接产生的无用内容。

不得先写生产代码再补“证明性”测试。环境缺失应记录并修复环境，不得放宽断言掩盖失败。

## 4. 验证分层

- 第一层：格式与结构——Harness 检查、JSON/schema、导入、lint。
- 第二层：行为——单元、集成、GUI offscreen、固定 fixture。
- 第三层：授权——diff、未跟踪文件、敏感数据、外部写入和未授权重构检查。
- 第四层：人工/live——仅在明确授权后运行真实数据源、API、通知和可见 GUI。

详细命令见 `docs/TESTING.md`。只声明本轮实际运行并看到通过的验证；未运行项目必须注明原因。

## 5. Review 与交接

交接必须包含：

- 改变了什么，以及为什么是最小充分改动。
- 实际运行的命令、结果与失败数。
- 未验证内容及原因。
- 外部影响、授权证据和推送目标。
- 后续任务，但不得把未完成项表述为已完成。

高风险改动至少做一次独立语义审查：重点检查提示词/策略语义、交易安全不变量、密钥泄漏和授权范围。

## 6. 外部影响闸门

以下操作必须有用户本轮明确授权：

- 推送分支、创建 PR/Issue、发布、部署。
- 发送飞书/PushPlus 消息或调用真实模型 API。
- 使用真实 MT5/TradingView/Tushare 等账户。
- 删除、覆盖、迁移用户配置、记录或经验数据。

只读的 `fetch`、日志检查和本地验证不自动授权后续写操作。

## 7. 失败回收

出现以下情况时，不只修当前症状：

- 重复 bug：增加回归测试或 eval case。
- 入口难找：更新 `AGENTS.md` 的地图。
- 命令漂移：更新 `docs/TESTING.md` 和机械检查。
- 任务范围经常误判：更新 Issue/PR 模板中的授权字段。
- 传感器错误难以行动：改进错误信息，使其指出文件和修复方向。

稳定经验进入版本化规则、测试或 eval；临时状态和单次流水账不进入入口文档。
